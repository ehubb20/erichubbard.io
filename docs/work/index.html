Three things I’ve built, and the decisions that don’t show in the output

One automation product, one integration, one analysis. Each one is written up for the decisions behind it, not just the output.

Note. Client names, employers, account identifiers, colleague names, hostnames and schema names have been removed throughout, and every figure shown is synthetic. Dates, decisions and reasoning are unchanged.

01
automation · 2026 · in weekly use

The weekly business review that builds itself

A packaged automation that assembles an exec-ready weekly deck for a marketplace account out of five separate systems: warehouse metrics, Linear, Asana, Zendesk, and a shared customer tracker. Twelve scripts, one JSON config per account, its own SQL and house style guide.

The engineering was the easy half. A weekly review is a document people argue with out loud, so the design constraint was never speed. It was that the deck must never be confidently wrong. Most of the work went into failing closed on stale data, distinguishing “source not checked” from “no activity,” and catching a permissions bug that returned a plausible-looking subset instead of an error.

The case study covers the architecture and the stack: the run as a chain of artifacts, the build, validate, publish ordering that keeps a bad deck from reaching a reader, and the four validation layers, each with its own blind spot written down beside it.

Integration · 2026 · Nightly

The API said yes and did nothing

An order ships in five boxes and the buyer can only see one of them. The sync between the order management system and the marketplace records a single tracking number per order, so every additional package arrives untracked as far as the customer is concerned. Support absorbs the difference, one “where is the rest of my order” at a time.

The finding that shaped everything else: the editable window is gated on delivery, not on fulfilment. Once an order shows a delivery time, additional tracking is accepted and silently discarded. Nothing errors. So the job has to run the same night, while the packages are still moving, and read the delivery timestamp before it writes anything.

The modern REST fulfilment endpoint has the same problem in a different place. On a line that is already fulfilled it returns a created response and then does nothing at all. The older Trading call accepts a list of tracking numbers and actually writes them, so that is the one the job uses. It was proven on an eight-package order, all eight now on the record.

Tracking is stored per line item rather than per order, and the order management system’s item number turns out to be the marketplace’s line identifier, so every package maps to the line it belongs to. The job sends one call per line carrying that line’s complete set. Never order level: an order-level call copies a single tracking number onto every line, which is worse than doing nothing because it looks like it worked.

An append-only log is the memory. It de-duplicates the two-day selection window, so the deliberate day-to-day overlap heals a missed run instead of sending twice; it drives retries, because a failed row is picked up again the next night and a sent row is not; and it is the audit trail. A tracking number that ties to no line at all is logged for a person rather than guessed at, and nothing writes without an explicit execute flag. A seven-day catch-up considered 129 orders and could act on 9. The other 120 had already delivered, which is the whole argument for a nightly job rather than a cleanup script.

What I take from it: a success response is not evidence that anything happened. Both ways this could fail quietly returned success. The job trusts observable state, the delivery timestamp and its own log, over anything the API says back.

Analysis · 2026

What returns actually cost, and what the data would not tell us

A question that sounds like one query: what do marketplace returns cost us, and why are customers returning things? The answer took four cuts: revenue impact by marketplace, returned dollars by reason, the worst-offending titles under “not as described,” and returns as a share of gross sales.

Most of the effort went into decisions that never appear in the output. The obvious join key was the wrong one: matching returns to order lines on the channel line id matched 82% of rows, because one marketplace’s line ids do not align. Matching on order plus SKU matched 96%. The refund amount field was about 90% null, so returns had to be priced off the originating order line instead. Line price is per unit, and order lines need deduplicating to one row per order and SKU before joining, or multi-line units double-count. Each of those is documented in the query header, because the next person to run it will otherwise rediscover them the expensive way.

The part of this I would put in front of a hiring manager is not the chart. It is the header of the query:

-- Returns revenue impact by marketplace and reason.
--
-- Join returns -> order_lines on (channel_order_id, channel_sku), NOT on the
-- channel line id: 96% match vs 82%. One marketplace's line ids don't align.
--
-- refund_amount is ~90% NULL on this source. Price the return off the
-- originating order line instead of trusting the refund field.
--
-- line_item_price is PER UNIT. Returned revenue = line_item_price * return_qty.
-- Dedupe order_lines to one row per (order, sku) before joining, or units
-- with multiple lines double-count.

with lines as (
  select channel_order_id, channel_sku,
         any_value(line_item_price) as unit_price
  from   order_lines
  group by 1, 2                     -- one row per (order, sku)
)
select   r.marketplace,
         r.reason_category,
         sum(l.unit_price * r.return_quantity) as returned_revenue
from     returns r
join     lines   l using (channel_order_id, channel_sku)
group by 1, 2
order by returned_revenue desc;

The limit worth stating. “Not as described” is the largest bucket, and it is also the least informative, because it is a dropdown selection rather than an explanation. One marketplace exposes the buyer’s free-text comment through its post-order API, so I wrote a second script to pull verbatims per return and read them. The largest marketplace has no equivalent. Neither its API nor the warehouse carries buyer free-text, only the reason code.

So the qualitative depth behind this chart exists for part of the business and cannot exist for the rest. That belongs in the deliverable, stated plainly, rather than being quietly papered over by presenting one channel’s verbatims as if they described all of them.
