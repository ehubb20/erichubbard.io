Automation · 2026 · in weekly use

The weekly business review that builds itself

A packaged agent skill that assembles an exec-ready weekly deck for a marketplace account out of five separate systems — warehouse metrics, Linear, Asana, Zendesk, and a shared customer tracker. Twelve scripts, one JSON config per account, its own SQL and house style guide.

The engineering was the easy half. A weekly review is a document people argue with out loud, so the design constraint was never speed — it was that the deck must never be confidently wrong. Most of the work went into failing closed on stale data, distinguishing "source not checked" from "no activity," and catching a permissions bug that returned a plausible-looking subset instead of an error.

Architecture · 2026

Three layers for eight marketplace APIs

Customer service operations touched eight external systems, each with its own auth model — two-layer token exchange with request signing on one, OAuth refresh on another, stateless basic auth on a third. Every new automation re-solved the same problems, and business logic kept getting welded to whichever API it happened to start from.

The fix was a strict three-layer split. Connectors know one API each and contain no business logic — they expose what the API can do, output JSON, and compose. Jobs orchestrate connectors to accomplish exactly one business outcome, end to end, independently. Pipelines chain jobs into multi-step workflows.

The third layer does not exist yet, and the documentation says so in those words. Naming the empty layer is what stops the next person quietly implementing it inside a job — which is how the original tangle formed.

Analysis · 2026

What returns actually cost, and what the data would not tell us

A question that sounds like one query: what do marketplace returns cost us, and why are customers returning things? The answer took four cuts — revenue impact by marketplace, returned dollars by reason, the worst-offending titles under "not as described," and returns as a share of gross sales.

Most of the effort went into decisions that never appear in the output. The obvious join key was the wrong one: matching returns to order lines on the channel line id matched 82% of rows, because one marketplace's line ids do not align — matching on order plus SKU matched 96%. The refund amount field was about 90% null, so returns had to be priced off the originating order line instead. Line price is per unit, and order lines need deduplicating to one row per order and SKU before joining, or multi-line units double-count. Each of those is documented in the query header, because the next person to run it will otherwise rediscover them the expensive way.

The part of this I would put in front of a hiring manager is not the chart. It is the header of the query:

-- Returns revenue impact by marketplace and reason.
--
-- Join returns -> order_lines on (channel_order_id, channel_sku), NOT on the
-- channel line id: 96% match vs 82%. One marketplace's line ids don't align.
--
-- refund_amount is ~90% NULL on this source. Price the return off the
-- originating order line instead of trusting the refund field.
--
-- line_item_price is PER UNIT. Returned revenue = line_item_price * return_qty.
-- Dedupe order_lines to one row per (order, sku) before joining, or units
-- with multiple lines double-count.

with lines as (
  select channel_order_id, channel_sku,
         any_value(line_item_price) as unit_price
  from   order_lines
  group by 1, 2                     -- one row per (order, sku)
)
select   r.marketplace,
         r.reason_category,
         sum(l.unit_price * r.return_quantity) as returned_revenue
from     returns r
join     lines   l using (channel_order_id, channel_sku)
group by 1, 2
order by returned_revenue desc;

The limit worth stating. "Not as described" is the largest bucket, and it is also the least informative — it is a dropdown selection, not an explanation. One marketplace exposes the buyer's free-text comment through its post-order API, so I wrote a second script to pull verbatims per return and read them. The largest marketplace has no equivalent — neither its API nor the warehouse carries buyer free-text, only the reason code.

So the qualitative depth behind this chart exists for part of the business and cannot exist for the rest. That belongs in the deliverable, stated plainly, rather than being quietly papered over by presenting one channel's verbatims as if they described all of them.
